How it works

Four steps, the same every time

  1. 1

    Pair

    Plug in two drives and press n. btpair writes a small .backuptool/ folder to each: the pair it belongs to, its role, and its partner's volume UUID. From then on btpair recognizes main and replica by themselves — names don't matter.

  2. 2

    Plan

    Pick the extra steps for this run. Each checks first whether it has anything to do, so you see “up to date” before committing. A dry run lists every file that would be copied or removed.

  3. 3

    Mirror

    btpair locks the main drive read-only, measures the work with a dry pass, then mirrors with rsync. Anything the replica would lose — deleted or overwritten — moves to a dated trash folder instead.

  4. 4

    Record

    Status, stats, errors and anything left pending are written to both drives. Plug them into any Mac later and btpair knows when they last synced and how it went.

Safety

Built not to lose your data

Each guarantee is enforced in code and pinned by an automated test. The tests themselves were checked by deliberately breaking every mechanism and confirming they fail.

The main drive is read-only

Before copying, btpair remounts the main drive read-only and verifies it. Even a bug can't write to it.

Nothing is deleted outright

Files removed or overwritten on the replica move to .backuptool/trash/<run>. The last few runs are kept.

Suspicious runs stop early

An empty main drive, a replica short on space, or a run that would delete more than 25% of the replica all stop before anything changes.

It knows its drives

Drives are matched by volume UUID and re-checked right before syncing. Cloned metadata, two mains or a swapped drive block the pair.

Interruptions are visible

Both drives are marked “in progress” before anything changes, so a run that died midway is flagged and completed next time.

Look before you leap

A dry run previews every change without writing a byte. Checksum mode compares contents when size and date can't be trusted.

Extra steps

Backups are more than copying files

Steps run against the main drive before mirroring, so whatever they produce reaches the replica too. Each one plans first and keeps its own state, so repeat runs only do new work.

  • Prototype a step in config as a shell command — no recompiling
  • Report progress with simple ::progress and ::item lines
  • Skip work that's already done with skip_if
  • Promote it to Go when it grows up

~/.config/btpair/config.toml
[steps.notes]
type    = "shell"
title   = "Export notes"
default = true

# exit 0 = up to date; the output becomes the summary
skip_if = '''
test -f "$BT_STATE_DIR/done" && echo "exported today"
'''

run = '''
echo "::progress 1 2"
export-notes --to "$BT_MAIN/Notes"
echo "::progress 2 2"
touch "$BT_STATE_DIR/done"
echo "exported 42 notes"     # last line = result
'''

On the drive

The drives remember, not the laptop

All metadata lives in a plain-JSON folder at the root of each drive, never copied between them. It's what tells btpair which drive is which, whether the last run finished, and what's still pending — on any Mac you plug them into.

Get started

Up and running in a minute

Terminal
# macOS ships an old rsync; btpair needs 3.1+
brew install rsync

git clone https://github.com/tryshchenko/btpair.git
cd btpair
make build
./bin/btpair

No spare drives handy? make debug && make dev builds folders that act like drives — a drifted pair, an unplugged one and two blanks — so you can try everything safely.
